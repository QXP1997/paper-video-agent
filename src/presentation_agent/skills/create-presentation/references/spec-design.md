# Spec 设计与证据规则

## 适用输入

先判断输入属于哪一类，再选择合适的证据粒度：

- **论文或 PDF**：记录论文、解析结果和图表页码；结论必须能回到页码或图表。
- **博客或网页**：记录 URL、标题和访问时间；区分作者原话、页面事实和自己的解释。
- **技术文档或教程**：记录版本、章节和 API 名称；不要把推测写成官方行为。
- **数据集或实验结果**：记录数据来源、单位、筛选条件和计算口径。
- **用户笔记或问题描述**：记录为 `note`，明确哪些内容是用户提供的背景，哪些内容仍需验证。

## `SlideDeckSpec` 最小结构

```json
{
  "schema_version": "1.0",
  "title": "主题名称",
  "audience": "目标听众",
  "language": "zh-CN",
  "aspect_ratio": "16:9",
  "sources": [],
  "assets": [],
  "slides": []
}
```

每页都要有 `id`、`title`、`purpose`、至少一个 `elements`、`speaker_notes` 和可解析的引用。内容页通常只承担一个清晰目的；封面保持简洁，结论页需要区分“材料明确支持的结论”和“后续推断”。

## 视觉资产

- 已存在的图、表、公式或代码截图登记 `path`，并附来源定位。`path` 必须相对最终
  `deck_spec.json` 所在目录填写，因为 PPTX 渲染器从 Spec 目录解析素材路径。
- 需要生成的非事实性装饰素材登记具体 `prompt` 和生成器；没有真实文件时，不得声称已生成。
- 可从数据重建的表格和图表尽量登记 `data`，使 PPTX 后端能够生成可编辑对象。
- `build_steps` 是跨后端意图，不把它当成已经完成的 PPT 动画。

## 校验

```text
python -m research_presentation_core validate <deck_spec.json>
```

校验失败时先修复来源、资产、元素和动画引用，再进入 PPTX 阶段。不要在渲染器里偷偷补内容来绕过校验。
